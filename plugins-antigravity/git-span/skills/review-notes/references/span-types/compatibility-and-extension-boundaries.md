# Compatibility and extension boundaries

Scope: find and declare spans during behavioral review using compatibility and extension boundaries.

## When to use this type

An extension could impose new requirements on behavior that remains explicitly supported. Historical permissiveness alone creates no compatibility obligation; do not add adapters or fallbacks without task authority.

## Information and anchors

Name the supported earlier specimen, new boundary it crosses, promised observation, scope/version and authorised retirement condition.

Candidate anchor roles: compatibility authority; earlier invocation/specimen; new dispatcher or mode gate; retained execution path. Select existing content carrying the rule or likely to be encountered at the risky decision. These are roles, not a required anchor count.

## Review and add

1. Begin with the reviewed change and affected consumer: Check whether broadened discovery, shared validation or new defaults impose prerequisites outside their authorised scope.
2. Establish the rule independently of the changed implementation. Distinguish a defect, an authorised change and an unresolved requirement before editing metadata.
3. Obtain or propose applicable distinguishing evidence: Send a supported earlier input through the new boundary and verify its actual result, not a trivial path that bypasses the extension.
4. Inspect existing spans at the changed site and participating locations. Extend a useful existing span; otherwise propose a new span carrying this rule and scope, then follow step 5b in [the skill](../../SKILL.md). A useful single-anchor reminder is eligible.
5. Report the changed decision, evidence limits and unresolved finding to the parent. Leave span edits unstaged; the parent owns production edits, validation and commits.
