# Compatibility and extension boundaries

Scope: reassess an existing span before refreshing it using compatibility and extension boundaries.

## When to use this type

An extension could impose new requirements on behavior that remains explicitly supported. Historical permissiveness alone creates no compatibility obligation; do not add adapters or fallbacks without task authority.

## Information and anchors

Name the supported earlier specimen, new boundary it crosses, promised observation, scope/version and authorised retirement condition.

Candidate anchor roles: compatibility authority; earlier invocation/specimen; new dispatcher or mode gate; retained execution path. Select existing content carrying the rule or likely to be encountered at the risky decision. These are roles, not a required anchor count.

## Reassess and reconcile

1. Use the current why, anchor bytes and history from stage 3 of [the procedure](../procedure.md). Check whether broadened discovery, shared validation or new defaults impose prerequisites outside their authorised scope.
2. Confirm authority and meaning before refreshing content. Preserve unresolved disagreements; return behavior findings to the owner.
3. Select evidence appropriate to the semantic change: Send a supported earlier input through the new boundary and verify its actual result, not a trivial path that bypasses the extension.
4. Refresh unchanged identities or atomically replace moved paths/ranges under the procedure. Revise the why when its rule or scope changes; extend, split or consolidate only when the information requires it.
5. Retain useful explanation even when tested or reduced to one anchor. Retire only when the relationship/reminder is obsolete or adds no useful decision context. Require scoped zero drift; delegated work stays unstaged for the owner.
