# Cross-backend behavioral equivalence

Scope: reassess an existing span before refreshing it using cross-backend behavioral equivalence.

## When to use this type

Parallel backends or platform copies promise equivalent behavior despite native differences. Keep one coherent relationship rather than one span per mirrored pair; a check does not by itself remove the value of its explanation.

## Information and anchors

Name the common authority, semantic slice, backend-specific mechanisms, permitted differences and representative coverage limit.

Candidate anchor roles: common specification/value model or normative input; emitter/adapter implementations; parity or conformance observation. Select existing content carrying the rule or likely to be encountered at the risky decision. These are roles, not a required anchor count.

## Reassess and reconcile

1. Use the current why, anchor bytes and history from stage 3 of [the procedure](../procedure.md). Check whether one backend changed semantics, a parity check omits an exception, or regenerated copies differ from the normative input.
2. Confirm authority and meaning before refreshing content. Preserve unresolved disagreements; return behavior findings to the owner.
3. Select evidence appropriate to the semantic change: Compare the same discriminating case across relevant backends; inspect type, mutation identity, async completion or intentional differences.
4. Refresh unchanged identities or atomically replace moved paths/ranges under the procedure. Revise the why when its rule or scope changes; extend, split or consolidate only when the information requires it.
5. Retain useful explanation even when tested or reduced to one anchor. Retire only when the relationship/reminder is obsolete or adds no useful decision context. Require scoped zero drift; delegated work stays unstaged for the owner.
