# Span evidence and anchor guidance

Scope: Use before declaring or redesigning a span. Return to [the declaration recipe](../SKILL.md#declare-a-new-coupling).

## Authority and specifications

Preserve actual decisive requirement wording and its source; examples in type references
are illustrative. Reuse an owning repository specification, issue/RFC record or decision
within task authority. Anchor requirement, implementation and relevant test where useful.
For uncommittable requirements, quote a short decisive phrase and source in the why;
label it unverified. Preserve chat-only requirements using repository conventions; ask
only if destination, disclosure or authority is unclear. Keep private material private,
quotes short and licensing respected.

Link later clauses to requirements they amend or supersede. For consequential, disputed
or hard-to-reverse interpretations, record scope, alternatives, supporting authority and
what evidence would reopen the decision. Label assumptions. Committed code and rationale
show intent; neither supersedes requirements without authorised evidence. A decision
record or anchored transcript does not itself authorise a behavior change.

## Anchor and delivery design

Use existing file paths or inclusive ranges, never directories or nonexistent future files.
Anchor the decisive rule and likely decision point; several ranges in one file are valid.
Use a whole file for unit identity or deliberate broad context; narrower ranges reduce
unrelated drift. Generated output is eligible for emitted structure or a concrete witness;
prefer stable inputs when they carry the same information and repair the generator.
A one-anchor reminder can carry external knowledge but has no anchored counterpart whose
change would expose disagreement. State that limit rather than inventing a second anchor.

Hook delivery depends on supported operations, attribution, file eligibility and session
suppression. The anchor list does not load counterpart bodies. Identify a likely read/edit
and the decision the why changes; inspect spans explicitly if delivery is uncertain.
Do not assume replay, directory watches, remote drift detection or executable predicates.

## Test context and utility

Test-covered relationships are eligible when timely explanation preserves a surprising
contract or guides a decision before execution. Do not duplicate a test catalog without
adding useful context. Optionally record `Checked by <repository-relative test file and
test name>: <observation>. Not checked: <residual obligation>.` State complete coverage
accurately when there is no residual obligation. Do not create a test merely to fill this
convention. Inspect the test and package runner; confirm collection or run a focused check
when needed. Missing tests invalidate references; absent references mean unknown protection.
Named tests do not limit checks for credible impact on dependencies, formats, defaults
or consumers outside the anchors. Keep long commands in the owning test/document.
For consequential interface changes or behavior-preserving transformations, follow
`git-span:review-notes` § Boundary review.

Assess information, knowledge timing, feasible anchors, likely delivery, changed decision,
verification and maintenance separately. A later discovery can prevent recurrence without
proving earlier knowledge. Extend or combine shared rules; split independent authority or
update rhythms. Retain useful tested/single-anchor reminders; retire obsolete or valueless
context. Zero drift records content agreement, not correctness or review completion.
