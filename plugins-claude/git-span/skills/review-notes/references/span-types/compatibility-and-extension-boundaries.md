# Compatibility and extension boundaries

Scope: add and update spans for compatibility and extension boundaries.

## When to use this type

An extension could impose new requirements on behavior that remains explicitly supported. Historical permissiveness alone creates no compatibility obligation; do not add adapters or fallbacks without task authority.

## Information and anchors

Name the supported earlier specimen, new boundary it crosses, promised observation, scope/version and authorised retirement condition.

Candidate anchor roles: compatibility authority; earlier invocation/specimen; new dispatcher or mode gate; retained execution path. Select existing content carrying the rule or likely to be encountered at the risky decision. These are roles, not a required anchor count.

## Add or update a span

1. Locate the rule and participating locations using the anchor roles above. Preserve its authority, scope and evidence limits in the why.
2. Inspect existing spans at those locations. Extend useful coverage; otherwise add a span following step 5b in [the skill](../../SKILL.md). A useful single-anchor reminder is eligible.
3. Update anchors and the why when the relationship changes; preserve unresolved authority or interpretation explicitly.

## Illustrative why

> Manifest-based ingestion preserves the supported single-file invocation without a manifest; manifest validation belongs to multi-source mode.

This example supplies no authority for another repository. Substitute its actual contract and scope; quote decisive requirement wording where available.
